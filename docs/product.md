# プロダクト定義

企画の正本。実装中に判断へ迷ったら、ここの設計原則に立ち返る。

## 課題

STECH、NxTENDO、LinkedIn Student Club、IDEACTIVE など複数の学生コミュニティや
ハッカソンに参加する中で、**出会った人を覚えきれない・思い出せない**。

特に「記録すること自体を忘れる」という、記憶が苦手な人特有の矛盾がある。
記録アプリを入れても、記録する習慣が続かなければ意味がない。

## コンセプト

記録を「覚える努力」に頼らず、**「思い出させる仕組み」**で解決する。

- 入力の手間を極限まで減らす(数秒で記録が終わる)
- 想起はアプリ側から能動的に働きかける(ユーザーが思い出そうとしなくてよい)

人に栞を挟んでおき、必要なときにそのページが開かれる。「ひとしおり」の名前の由来。

## ターゲットユーザー

複数のコミュニティ・イベントに掛け持ちで参加し、人脈管理に課題を感じている学生・社会人。
まずは開発者自身が一人目のユーザー。**MVP は単一ユーザー前提で、認証は作らない。**

## 設計原則

実装のトレードオフはすべてこの 3 原則で判断する。

1. **入力摩擦をゼロに近づける**
   - 記録は 1 画面で完結。名前(あだ名・曖昧可)+ ワンタップのタグ + 音声メモ
   - 必須項目は名前だけ。他は全部あとから埋められる
2. **想起を自動化する**
   - しばらく会っていない人をバッチで抽出し、**1 日 1 人だけ**通知する
   - 1 日 1 人に絞るのは、通知疲れで無視される状態を避けるため
3. **継続させる(精度より継続優先)**
   - 曖昧な名前でも登録でき、後から修正できる
   - 記録忘れを咎めない。「○日記録していません」のようなネガティブな煽り通知はしない
   - 思い出す対象がいない日は通知しない(無理に出さない)。ただし MVP はローカル通知のため
     配信時にサーバーへ問い合わせできず、通知自体は毎日鳴る。開いたときに対象がいなければ
     通常の記録画面をそのまま見せ、「いない」ことを強調しない。APNs 導入時に再検討する

## MVP スコープ

### 入れるもの

1. **Encounter(出会い)記録**
   - 「誰と・いつ・何を話したか」を、名前 + タグのワンタップ + 音声メモで記録
   - 音声はオンデバイスで文字起こしし、テキストとして保存
2. **人の一覧・詳細・修正**
   - 記録した人の一覧、1 人の詳細(接触履歴つき)、名前・メモの事後修正
3. **想起通知バッチ**
   - 30 日以上会っていない人から 1 日 1 人を選ぶ日次バッチ(Solid Queue)
   - iOS はローカル通知でユーザーに知らせ、アプリ内で「今日の一人」を表示

### 入れないもの(明示的に後回し)

| 項目 | 理由 / 再検討タイミング |
|---|---|
| 認証・複数ユーザー | 開発者自身が使えれば MVP は成立。公開時に再検討 |
| APNs(リモートプッシュ) | 証明書・サーバ実装のコストが重い。MVP はローカル通知で代替 |
| EventKit(カレンダー連携) | 「どのイベントで会ったか」の自動補完は想起の質を上げるが記録の必須要素ではない |
| サーバ側の音声・自然言語処理 | 文字起こしはオンデバイスで足りる。構造化(名前/タグ自動抽出)は継続が確認できてから |
| 人物の名寄せ(同名マージ) | MVP では別人として登録し、クライアントの入力補完で運用回避 |
