# ロードマップ

MVP 全体の流れと、計画に効いた決定の記録。
**タスクの詳細・受け入れ条件は `task` ラベルの GitHub issue、進捗は追跡 issue [#22](https://github.com/ruribou/hitoshiori/issues/22) が正。**

## 全体像

```
Phase 0  環境構築                     ✅ 完了
Phase 1  Backend: 記録 API            タスク 01 → 02 → 03
Phase 2  iOS: 記録フロー              タスク 04 → 05 → 06, 07
Phase 3  想起ループ                   タスク 08 → 09
Phase 4  磨き込み・実運用開始          使ってから決める
```

- Phase 1 と 2 で「数秒で記録できる」を作り、Phase 3 で「アプリが思い出させる」を閉じる
- backend(01〜03, 08)と iOS(04〜07, 09)は依存が切れていれば並行して進めてよい
  (例: 03 と 04 の並行、08 は 02 完了を待たず着手可)

## 各フェーズの狙い

| Phase | 狙い | 完了の定義 |
|---|---|---|
| 1 | 記録系 API 一式(スキーマ確定・テスト付き) | curl で docs/api.md 通りに記録・閲覧・修正ができる |
| 2 | 入力摩擦ゼロの記録体験(設計原則 1) | 起動 → 名前 → タグ → 保存が 10 秒以内。音声メモが動く |
| 3 | 想起の自動化(設計原則 2) | 毎日 1 人選ばれ、通知から「この人と何を話したか」に 2 タップで到達 |
| 4 | 実運用からの改善 | 開発者自身が毎日使っている |

## Phase 4 の候補(使ってみてから優先順位を決める)

- 通知文言に人物名を入れる(APNs 導入 or バックグラウンドフェッチの検討)
- EventKit でカレンダーの予定から「どこで会ったか」を補完
- 同名人物のマージ(名寄せ)
- 想起しきい値(30 日)・通知時刻の設定画面
- デプロイ(単一ユーザーのうちは自宅サーバ / 安価な VPS で十分)

## 決定事項ログ

計画に効いた判断の記録。覆すときはここに追記してから変える。

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-08-14 | ジョブは Sidekiq/Redis でなく Solid Queue | Redis 不要・recurring.yml で定期実行が完結(環境構築時決定) |
| 2026-08-14 | MVP は認証なし・単一ユーザー | 一人目のユーザーは開発者自身。公開時に再検討 |
| 2026-08-14 | 音声はオンデバイス文字起こしのみ、サーバは平文保存 | 入力摩擦の低減が目的であり、構造化は継続実績を見てから |
| 2026-08-14 | 通知は APNs でなくローカル通知(定時固定) | 証明書・配信サーバのコスト回避。想起体験の検証には十分 |
| 2026-08-14 | 名寄せしない(同名は別人として登録) | 精度より継続優先。入力補完で運用回避できる |
| 2026-08-14 | `last_encountered_at` は people に非正規化 | 想起バッチの抽出条件。都度 MAX 集計を避ける |
| 2026-08-14 | サーバの TZ は Tokyo(`config.time_zone`) | 「今日の 1 人」「毎朝のバッチ」の日付判定を JST に揃える |
| 2026-08-14 | 実装計画は docs/tasks/ に 1 タスク 1 ファイルで管理 | エージェントに 1 タスク単位で渡せる粒度にするため |
| 2026-08-15 | 実装計画を GitHub issue へ移行(docs/tasks/ は廃止) | 進捗表の手動更新が破綻したため。PR の `Closes #N` でマージ時に自動クローズされる。git 管理外だった指示書が別クローン・CI からも参照できるようになる |
