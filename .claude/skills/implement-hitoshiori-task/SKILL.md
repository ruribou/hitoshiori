# ひとしおりのタスクを実装する

番号付きタスクを1つだけ選び、そのスコープと受け入れ条件を守って完了可能な状態まで進める。
リポジトリ内のドキュメントを正本とし、このskillに仕様を複製しない。

## 1. 対象タスクを決める

1. `git rev-parse --show-toplevel`でリポジトリルートを特定し、以降のパスをルート基準で扱う。
2. タスクの正本は`task`ラベルの付いたGitHub issue。全体像と依存グラフは追跡issue(`gh issue view 22`)にある。
3. ユーザーが番号を指定した場合は、その番号のissueを対象にする。タスク番号(`05`など)で指定された場合は、issueタイトル先頭の番号と対応させて特定する。
4. 「次のタスク」と依頼された場合は、`gh issue list --label task --state open`のうち、依存issueがすべてクローズ済み、または受け入れ条件を満たしたopen PRが存在するものから、タイトル番号が最も若いものを選ぶ。
5. issueが取得できない場合(認証・ネットワーク不通など)は、`docs/plan.md`から次の作業を特定し、詳細な受け入れ条件がないことを明示する。推測で大きなスコープを補わない。
6. 指定タスクの依存issueが未クローズでも、依存タスクの受け入れ条件がすべて満たされ、open PRのheadブランチが存在する場合は、そのブランチ上でStacked PRとして着手できる。それ以外は、独立して安全に進められる範囲がissue本文に明記されている場合だけ着手し、該当しなければ依存関係を根拠に停止する。
7. 同時に複数タスクを実装しない。ユーザーが明示的に複数指定した場合は、依存順に1件ずつ進める。

## 2. 作業前の状態を確認する

1. `git status --short --branch`を確認する。
2. 既存の変更をユーザーの作業として保持し、無関係な差分を編集、stage、破棄しない。
3. 対象ファイルと既存差分が重なる場合は、内容を読んで安全に統合する。意図を判断できない競合だけをユーザーへ確認する。
4. `AGENTS.md`を読み、そこに記載されたドキュメントを指定順で読む。
5. 少なくとも次を確認する。
   - `docs/product.md`: 設計原則とMVPスコープ
   - 追跡issue(`gh issue view 22`): 依存関係と進捗
   - 対象issue(`gh issue view <番号>`): やること、やらないこと、実装メモ、受け入れ条件
   - タスクが参照する`docs/schema.md`または`docs/api.md`
6. 着手時に対象issueへ`status:in-progress`ラベルを付ける(`gh issue edit <番号> --add-label status:in-progress`)。すでに付いていれば維持する。
7. ユーザーがPR不要と明示していなければ、対象タスク用ブランチ`feature/task-NN-<slug>`を作成する。`NN`はissueタイトル先頭のタスク番号。すでに正しいブランチなら維持する。
8. 通常は既定ブランチをPRのbaseにする。未マージの依存タスクを土台に実装する場合は、その依存PRのheadブランチから分岐し、同じブランチをbaseにするStacked PRとして扱う。複数の未マージ依存が別ブランチに分かれている場合は、勝手に統合せず方針を確認する。

## 3. 実装方針を固定する

1. タスクのゴールを1文で言い換える。
2. 「やること」を実装対象、「やらないこと」を明確な境界として扱う。
3. 仕様変更が必要なら、コードより先に正本ドキュメントを更新する。実装都合で文書を後追いさせない。
4. 次の同期規則を必ず守る。
   - APIエンドポイント、リクエスト、レスポンス、エラー形式を追加・変更する場合は、同じ変更で`docs/api.md`を更新する。
   - マイグレーションを追加・変更する場合は、同じ変更で`docs/schema.md`を更新する。
   - タスクの前提や受け入れ条件を変える場合は、対象issueの本文を先に更新し(`gh issue edit <番号> --body-file -`)、変更理由をコメントで残す。
5. 判断に迷ったら`docs/product.md`の設計原則を優先し、MVP外の機能を先回りして追加しない。
6. ユーザーがPR不要と明示した場合だけ、commit、push、PR作成を省略する。

## 4. 実装する

### Backend

- Docker Compose前提のコマンドを使い、ホストのRuby環境に依存しない。
- Railsコードを変更したら、対応するRSpecを同じ変更に含める。
- JSON契約は`docs/api.md`のキー、ネスト、null、日時、エラー形式までテストで固定する。
- Solid Queue、PostgreSQL、Tokyoタイムゾーンなど、`AGENTS.md`の固定事項を維持する。

### iOS

- Swift 6、SwiftUI、iOS 18.0以上、Strict Concurrency completeを維持する。
- ターゲット、Info.plist、権限を変える場合は`ios/project.yml`を編集し、生成された`.xcodeproj`を変更対象にしない。
- API通信は既存のクライアント層を経由し、Viewから直接通信しない。
- 入力失敗時の再入力や不要な必須項目など、記録摩擦を増やす実装を避ける。

## 5. 検証する

1. 変更に近いテストを先に実行し、失敗原因を修正する。
2. 対象タスクの「受け入れ条件」に書かれたコマンドと確認項目をすべて実行する。
3. backendを変更した場合は、原則として次を通す。

   ```bash
   docker compose exec backend bundle exec rspec
   ```

4. iOSを変更した場合は、原則として次を通す。

   ```bash
   cd ios
   xcodegen generate
   xcodebuild build -scheme Hitoshiori -destination 'platform=iOS Simulator,name=iPhone 17'
   xcodebuild test -scheme Hitoshiori -destination 'platform=iOS Simulator,name=iPhone 17'
   ```

5. `git diff --check`を実行する。
6. `git status --short`と差分全体を確認し、生成物、秘密情報、無関係な変更が入っていないことを確かめる。
7. 実機確認や外部状態など、その環境で実行できない受け入れ条件を成功扱いにしない。未確認の理由と人間が行う確認手順を対象issueへコメントで残す(`gh issue comment <番号>`)。

## 6. PRを作成する

1. ユーザーがPR不要と明示していない限り、受け入れ条件を満たした後に自動でcommit、push、PR作成まで行う。実装完了後に改めて許可を求めない。
2. 対象タスクのファイルだけをstageし、日本語のcommitメッセージでcommitする。無関係な既存差分を含めない。
3. 作業ブランチを`origin`へpushし、`gh pr create`でPRを作成する。PR本文には概要、変更内容、検証結果、依存PRを記載する。
4. **PR本文に`Closes #<対象issue番号>`を必ず含める。** これがマージ時のissue自動クローズと、追跡issueのチェックリスト更新の唯一の手段。書き忘れたまま報告しない。
5. Stacked PRでは直下の依存PRのheadブランチをbaseに指定し、PR本文へ依存先を明記する。依存なし、または依存PRがマージ済みなら既定ブランチをbaseにする。`Closes`は自タスクのissueだけに書き、依存タスクのissueには書かない。
6. PRは自動作成するが、自動マージはしない。
7. 認証、ネットワーク、権限、CI失敗でPRを作れない場合は成功扱いにせず、失敗した操作と再開手順を報告する。

## 7. 状態を更新して報告する

1. 対象issueを手動でクローズしない。クローズはPRマージ時の`Closes`に任せる。`status:in-progress`ラベルはマージまで維持する。
2. 未達の受け入れ条件がある場合は、その内容と理由を対象issueにコメントで残す。
3. 追跡issueのチェックリストは手で編集しない(対象issueのクローズで自動的に反映される)。
4. PRを作成した場合はURLとbase/headブランチを含め、最終報告を日本語で簡潔にまとめる。
   - 対象issue番号と達成したゴール
   - 主な変更
   - 更新した仕様文書
   - 実行した検証と結果
   - 未確認事項または残作業
   - 現在のissueの状態

## 完了判定

次をすべて満たしたときだけ「実装完了」と報告する。

- タスクの「やること」を実装している。
- 「やらないこと」へスコープを広げていない。
- 必要な仕様文書をコードより先に更新している。
- 必要なテストを追加し、実行可能な受け入れ条件をすべて通している。
- 実行不能な条件を未確認として明示している。
- ユーザーの既存変更を壊していない。
- ユーザーがPR不要と明示していなければ、push済みブランチからPRを作成し、その本文に`Closes #<対象issue番号>`を含めている。
