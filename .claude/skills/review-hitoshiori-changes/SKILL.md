# ひとしおりの差分をレビューして指示書に残す

レビュー結果は会話に流すだけでは消える。**必ず`.claude/reviews/<slug>.md`へ、
別のエージェントがそのまま修正に着手できる指示書として書き出す**。
書き出しを省略した場合、このskillは未完了とする。

判断基準はリポジトリ内のドキュメントを正本とし、このskillに仕様を複製しない。

## 1. レビュー対象を決める

1. `git rev-parse --show-toplevel`でリポジトリルートを特定し、以降のパスをルート基準で扱う。
2. 引数の指定に従って対象を決める。
   - PR番号: `gh pr view <番号>`と`gh pr diff <番号>`。baseはPRのbaseブランチ。
   - ブランチ名: そのブランチと、`git merge-base`で求めたbaseとの差分。
   - 指定なし: 現在のブランチが対象。open PRがあればそのbase、無ければ既定ブランチをbaseにする。
3. 未コミットの変更があれば対象に含め、指示書の「前提」にその旨を書く。
4. 差分が空、または生成物だけの場合は、レビューを捏造せず理由を報告して停止する。
5. 一度に複数のPRやブランチをまとめてレビューしない。指示書が混ざると修正時に追えなくなる。

## 2. 前提を集める

1. `AGENTS.md`を読み、そこに記載されたドキュメントを指定順で読む。
2. 少なくとも次を確認する。
   - `docs/product.md`: 設計原則とMVPスコープ。判断に迷ったらここが優先
   - `docs/api.md`と`docs/schema.md`: API・DBの契約(確定版)
   - 対象タスクの`docs/tasks/NN-*.md`があれば、やること、やらないこと、受け入れ条件
3. `git diff --stat <base>...HEAD`を控える。指示書の「差分の内訳」にそのまま貼る。
4. 依存バージョンを実ファイルで確認する(`backend/Gemfile.lock`、`ios/project.yml`など)。
   非推奨APIやフレームワーク挙動を指摘するなら、バージョンの裏取りが前提になる。

## 3. レビューする

組み込みの`code-review` skillを使ってよい。ただしその出力をそのまま転記せず、
必ず自分で該当コードを読んで裏を取る。

次の観点を順に見る。

1. **仕様との不整合**: `docs/api.md`・`docs/schema.md`・タスクの受け入れ条件と実装のずれ。
   実装が正しく仕様が古い場合も、どちらを直すかまで書く。
2. **バグ**: 500になる経路、データが壊れる経路、競合(同時実行、lost update、一意制約違反)。
3. **契約**: JSONのキー、ネスト、null、日時形式、エラー構造、HTTPステータス。
   iOSが固定の構造体でデコードする前提を壊していないか。
4. **テスト不足**: backendの変更にRSpecが伴っているか。異常系と境界値が固定されているか。
5. **性能**: N+1、不要なクエリ、ホットパスの無駄。
6. **設計・再利用**: コントローラ直書きのルール、後続タスクから再利用できない構造。
7. **規約違反**: 日本語で書くべき箇所、docsの同期漏れ(APIやマイグレーションを変えたのに
   `docs/api.md`・`docs/schema.md`が未更新)、進捗を仕様書側に持たせていないか。

ひとしおり固有の落とし穴も確認する。

- トランザクション内の`rescue`はPostgreSQLでは効かない(セーブポイントが要る)
- ジョブはSolid Queue。Sidekiq / Redisを前提にした指摘や実装は誤り
- iOSはSwift 6 / Strict Concurrency complete。`.xcodeproj`直接編集ではなく`ios/project.yml`
- 音声はオンデバイス文字起こし。サーバ側で音声・自然言語処理をしない(MVPの間)
- 記録摩擦を増やす実装(不要な必須項目、入力のやり直し)は設計原則違反として扱う

## 4. 指摘を検証する

指示書は他のエージェントがそのまま実行する。誤検出は無駄な修正を生むので、
書き出す前に1件ずつ確認する。

1. 該当ファイルを実際に読み、`file:line`が現在の内容と一致することを確かめる。
2. baseブランチ側に元からある問題か、この差分が持ち込んだ問題かを区別する。
3. 既に直っているもの、事実誤認だったものは黙って消さず、
   「対応不要と判断した指摘」へ理由付きで残す。
4. 再現手順を書けない指摘は、推測であることを明示するか落とす。
5. 優先度を付ける。
   - **P1**: バグ(500になる / データが壊れる)
   - **P2**: 契約・仕様の不整合
   - **P3**: 性能・設計
   - **P4**: ドキュメント

## 5. 指示書に書き出す

### 出力先

- `.claude/reviews/task-NN-<短いslug>.md`(タスクに紐づく場合)
- `.claude/reviews/<ブランチ名のslug>.md`(タスクに紐づかない場合)
- `.claude/reviews/`は`.gitignore`済み。**指示書をコミットやPRに含めない**。
- 同名ファイルが既にある場合は、未対応の項目を消さずに更新する。
  全て対応済みなら、対象コミットを冒頭に書いた上で新しい指摘に差し替えてよい。
- 指摘0件でも、対象と「指摘なし」を書いたファイルを残す。

### フォーマット

````markdown
# コードレビュー指摘の修正タスク(タスク NN: 見出し)

## 前提

- ブランチ: `<head>`(`<base>` からの差分をレビュー)
- 対象タスク: `docs/tasks/NN-*.md`(スコープの1行要約)
- 作業規約は `AGENTS.md` を読むこと。コミットメッセージ・コメント・docs は日本語
- テスト: `docker compose exec backend bundle exec rspec`
- 依存バージョン: Rails 8 / PostgreSQL 17 など、指摘の根拠になるもの

差分の内訳:

```
<git diff --stat の出力>
```

以下 N 件を優先度順に修正する。各項目に「修正方針」と「完了条件」を書いてあるので、
完了条件を満たすテストを追加した上で修正すること。

---

## P1: バグ(500 になる / データが壊れる)

### 1. <何が問題かを1行で>

- **場所**: `path/to/file.rb:12`
- **問題**: 原因を、コードの挙動に即して説明する
- **再現**: 具体的なリクエストと、実際に返るレスポンス
- **仕様**: `docs/api.md:32` のように、正本の該当箇所を行番号付きで示す
- **修正方針**: 直し方。落とし穴があれば明示する。まとめて直せる項目があれば番号で参照する
- **完了条件**: テストで示せる形で書く

## P2: 契約・仕様の不整合

## P3: 性能・設計

## P4: ドキュメント

---

## 対応不要と判断した指摘

- **<指摘>** という指摘があったが、確認したところ<根拠>。**対応不要**。

---

## 進め方の提案

1. まとめて直すのが効率的な塊
2. 各修正に必ずテストを追加する
3. 契約を変える修正は docs を先に直してから実装する
4. 最後に全テストを通す
````

各指摘には「場所」「問題」「修正方針」「完了条件」を必ず書く。
「再現」と「仕様」は該当する場合に書く。完了条件は検証可能な形にし、
「適切に修正する」のような判定できない書き方をしない。

## 6. 報告する

1. 書き出したファイルのパスを最初に示す。
2. 優先度ごとの件数と、最優先で直すべき数件を要約する。
3. 対応不要と判断した指摘があれば、その旨も伝える。
4. **修正はこのskillでは行わない**。修正を依頼されたら、指示書を起点に別途着手する。
5. レビュー対象の差分を、このskillの作業として変更しない。

## 完了判定

次をすべて満たしたときだけ「レビュー完了」と報告する。

- レビュー対象のbaseとheadを明示している。
- 正本ドキュメントと突き合わせて指摘している。
- 各指摘の`file:line`を実ファイルで確認している。
- 優先度を付け、各項目に修正方針と完了条件がある。
- 却下した指摘を理由付きで残している。
- `.claude/reviews/`配下にファイルを書き出し、パスを報告している。
- 指示書をコミットしていない。
